# Roadmap

Part of [Tower Defense PWA](./Tower%20Defense%20PWA.md).

## Direction

- Driver: learning/portfolio, not shipping a commercial product - favor depth of learning over speed of delivery.
- Stack: vanilla TypeScript + raw Canvas API, no game framework (Phaser/Kaboom/Pixi). Deliberate choice to learn the fundamentals (game loop, spatial logic, entity management) rather than abstract them away.
- Multiplatform = PWA install (manifest + service worker) + responsive canvas + unified input (Pointer Events for mouse/touch).

## v1 build order (complete)

Sequenced so each step is independently visible/testable and unblocks the next. Movement/combat come before economy/waves deliberately - those are the riskiest, most foundational systems, worth de-risking before layering balancing on top. PWA packaging is last on purpose: no point wiring installability before there's a game worth installing.

- [x] Repo scaffold - Vite/TS, game loop, canvas scale-to-fit, map data, board render.
- [x] Enemy movement - spawn one enemy, lerp along the path polyline to the core, despawn on arrival.
- [x] Core health - enemy reaching core costs HP; HP hits 0 → game over. Minimal HUD text.
- [x] Tower placement - Pointer Events click/tap-to-place on buildable tiles, range-circle preview, one tower type (Firewall Node) placed but inert.
- [x] Combat - tower targets nearest in-range enemy, spawns a projectile, projectile travels/hits/damages, enemy dies and despawns.
- [x] Economy - Cycles: earned on kill, spent on placement, HUD display, block placement when short.
- [x] Waves - timed spawner with a wave definition list (counts/types/timing), between-wave state.
- [x] Content pass - remaining tower types (IDS Scanner, Honeypot, AES Turret) + enemy types (Trojan, Packet Sniffer, Ransomware split-on-death) + Overclock ability.
- [x] PWA shell - manifest + icons + service worker (`vite-plugin-pwa`), verify installability/offline on mobile.
- [x] Boss + polish - Zero-Day boss, glitch kill-effect, win/lose screens.

## v1.1: Entity sprite pass (chosen 2026-07-12)

What and why: [Sprite Spec](./Design/Sprite%20Spec.md) - pixel art, 32px virtual tile (512x288 native), per-entity sizes where bulk encodes threat. Authoring: **pixel-strings in TS** (see Sprite Spec's Authoring section). Sequenced like v1: each step is independently visible/testable and unblocks the next. Renderer comes first because every later step draws into the virtual space it creates; the pipeline is proven on one sprite before any real art is made.

- [x] Virtual-resolution renderer - render the world to a 512x288 offscreen canvas (integer `VIRTUAL_TILE = 32` replaces the float `tileSize` in `render.ts` draw code), blit to the display canvas with `imageSmoothingEnabled = false`. Try integer scaling in device pixels (letterboxing the small remainder) first, keep plain scale-to-fit as a one-line fallback if the letterbox feels wasteful. Update `clientToGrid` for the blit offset/scale, round draw positions to whole virtual pixels (fractional coords antialias and break pixel purity). HUD text and end-screen overlays stay on the display canvas at full resolution. Prerender the static board once (banks part of the render-perf idea from [Idea Bank](./Idea%20Bank/Idea%20Bank.md)). Done: `canvas.ts` `Viewport`; integer scale w/ fractional fallback below 1x.
- [x] Pixel-string atlas pipeline - sprite format (string grid, one char per pixel, palette-char map), a startup baker that paints every sprite into one atlas canvas, a `drawSprite(name, frame, x, y)` helper, and a dev-only gallery view (`?gallery` - every sprite and frame at 8x, hot-reload friendly). Done: `sprites.ts` (baker + `drawSprite` + `spritePixels`), `gallery.ts`. Authoring detour: strings are emitted by `scripts/gen-sprites.mjs`, not hand-written (see Log).
- [x] Enemy sprites - all 6 kinds at spec sizes/ratios, 2-frame idle each, oriented in 90-degree steps to travel direction (never arbitrary rotation - keeps pixels crisp). Pull colors back toward the strict theme palette: shape and size now carry identity, so the current six-hue `ENEMY_VISUALS` rainbow can go. Done: `ENEMY_VISUALS` deleted; orientation via `directionAlongPath`.
- [x] Tower sprites - 4 kinds, silhouette encodes function per spec. Overclock states keep their procedural treatments (overheat dim, boost outline); IDS Scanner's sweep stays a procedural rotating line over the sprite. Done; muzzle-flash frame added for attack towers (`tower.flashMs`).
- [x] Board entities + projectiles - core mainframe (48x48), spawn port, projectile sprites (3x3, AES 5x5). Trace/board art untouched unless it visibly clashes with the new entities. Done; trace fill dimmed (`palette.traceFill`) so bright sprites read over it.
- [x] Glitch integration + verify - kill burst scatters the dead enemy's actual sprite pixels (colors/offsets sampled from the atlas - the spec's "now literal" payoff), then a full playthrough at several window sizes and DPRs, desktop + mobile viewport. Code done (`createGlitchBurst` takes `spritePixels`); the multi-size/DPR + physical-mobile playthrough is still pending manual QA, **carried into v1.2's verify step** below rather than done twice.

## v1.2: Tower panel + upgrades (chosen 2026-08-23)

What and why: [Tower Panel](./Design/Tower%20Panel.md) - a placed tower is currently a dead object with no stats, no upgrade, no undo, and its one interaction (arm `Q`, then click) is a keyboard mode in a game that is meant to be played on a phone. One selection model fixes all four, which is why [Idea Bank](./Idea%20Bank/Idea%20Bank.md) already flagged the panel as the foundation under upgrades, sell, and touch Overclock.

Sequenced like v1 and v1.1: each step is independently visible/testable and unblocks the next. Selection comes first because every later step acts on the selected tower; sell lands before upgrades because it is the smallest mutation that exercises the whole select-act-deselect loop.

- [x] Selection model - tap a placed tower to select, tap elsewhere or Escape to deselect; selection ring + range circle drawn in the world canvas. New branch in `main.ts`'s `pointerdown` ahead of the placement branch (the two targets are disjoint: `isPlaceable` already rejects `occupied` tiles). No panel yet.
- [x] Panel shell - DOM panel (toolbar's visual language, 44px targets, safe-area aware) anchored opposite the toolbar, showing the selected tower's name and stats, appearing and disappearing with the selection. Read-only.
- [x] Sell - `invested` on the `Tower` entity (placement + upgrades, tracked rather than recomputed), partial refund at 60%, frees the tile and clears the selection.
- [x] Upgrade tiers - `TOWER_STATS` becomes a per-kind array of 3 tiers, `towerStats(kind, tier)`, `tier` on the entity. Attack towers buy damage + fire rate, aura towers buy slow strength + radius (Honeypot's radius stays tight - a wide Honeypot is just an IDS Scanner). Panel shows current vs next tier. Tier tell stays procedural; no tier sprites this milestone.
- [x] Overclock migration - `OC` moves into the panel, the `overclockArmed` mode and the toolbar `OC` button go, `Q` stays as a shortcut acting on the selection.
- [x] Build preview (added mid-milestone 2026-08-23, not in the original six) - with a panel on screen, showing stats only *after* you have paid for a tower is backwards. The panel now has two modes: selected tower, or the tower about to be built (cost, stats, and the placement rule). Toolbar buttons stop being `disabled` when short on Cycles, since a disabled button swallows the tap you need to read what you are saving for.
- [x] Console restyle + dock (added mid-milestone 2026-08-23, not in the original six) - panel and toolbar stack in one bottom-centered dock instead of sitting in opposite corners, and the panel is styled as a green-on-black terminal (dot leaders, scanlines, blinking cursor) using only palette colors. Open by default, collapsible from its header bar.
- [x] Enemy inspection (added mid-milestone 2026-08-23, not in the original six) - tap an enemy to read it in the console: HP, speed, bounty, and its special rule (boss immunity, split-on-death), both of which were previously invisible. Selection became one tower-or-enemy union; `clientToGrid` split into `clientToWorld` plus a floor, since entities sit between tiles.
- [x] Verify - full playthrough, **plus the multi-size/DPR and physical-device QA still owed from v1.1 step 6**. Folded in here on purpose: v1.2 is the milestone that rewrites touch interaction, so testing the old flow on a phone first would have tested something about to be deleted. Done: played on a phone and reported clean, which also discharges the QA v1.1 owed.

## v1.3: The run - wave curve + pacing (chosen 2026-08-23)

What and why: [Run Structure](./Design/Run%20Structure.md) - a run is 4 waves and pays out ~228 Cycles over the 100 you start with, while taking one AES Turret to tier 3 costs 210. The three-tier ladder v1.2 just built is content the run is too short to reach, and v1.2 explicitly deferred the wave pass to whenever upgrades stopped moving. They have.

Sequenced like the milestones before it: pacing controls first because they are the tool that makes everything after them testable, the extraction before the harness because nothing outside a browser can step the sim today, and the curve before the preview because a preview of an untuned wave previews nothing.

- [x] Pause + speed toggle - 1x/2x multiplying the sim timestep, not the render rate; pause stops the sim and leaves rendering alive so the board and console stay readable while stopped. Lives with the console, not the build menu. Smallest step, isolated in `game-loop.ts` + `main.ts`, and the tool the rest of the milestone is tuned with. Done: `GameLoop.setTimeScale` scales the accumulator so the fixed tick survives; `||`/`1x` buttons in the console header; `Space` and `F` as shortcuts. Not seen running - the Chrome extension was disconnected again.
- [x] Extract the simulation - explicit state object + `stepGame(state, dtMs)` in its own module; `main.ts` keeps input, selection, render, DOM. **The checkpoint is that nothing changes** - no new behavior, no new numbers. Unblocks the harness and shrinks the project's biggest file. Done: `game.ts` (268 lines) owns state, stepping, placement, sell and upgrade; `main.ts` went 435 to 341. The kill burst's atlas lookup is injected as a hook so the sim imports no canvas. First tests in the project came with it (`npm test`).
- [x] Balance harness - headless script that runs the waves against a declared tower layout at a fixed timestep and reports leaks, core HP, and Cycles per wave. Cheap because the sim is already deterministic: the only `Math.random()` in `src/` is in the cosmetic glitch particles, and `tests/game.test.ts` already gates that property. Done: `src/balance.ts` (the run and the layouts, type-checked with the sim) plus `scripts/balance.ts` (`npm run balance`, formatting only). A layout is a build *order*, bought as the Cycles arrive, so it also answers whether a tier is reachable and not only whether it wins.
- [x] Wave curve - ~10 waves with a deliberate shape, each enemy kind introduced alone before it appears mixed (today wave 3 opens with 10 Packet Sniffers, the first ten the player has ever seen), economy sized so topping out some towers is reachable and topping out all of them is not. Tuned with the harness, confirmed by playing. Done: ten waves, a flawless run pays 409 against 570 to top out all four towers, and `tests/wave.test.ts` gates the introduction rule and the economy gap rather than trusting the prose. Three things the plan did not have, each forced by a harness reading and logged with its reason: spawn groups run **concurrently** inside a wave (`startMs`), waves past 6 carry an **HP multiplier** (`hpScale`), and the boss **costs 3 core HP** to breach. Confirmed in a browser only as far as a covered window allows - the full ten-wave playthrough is the next step's job.
- [x] Wave preview - console's fourth mode: with nothing selected between waves, read the composition of what is coming. Same surface as build/tower/enemy. Done: `nextWavePreview(spawner)` in `wave.ts`, a `renderWave` mode in the panel, and one flag in `main.ts` deciding which of the two unselected readings the console owns. The lull went 4s to 8s in the same step - a preview you cannot finish reading is not a preview, and step 6 is about to sell those seconds back.
- [x] Early-call bonus - calling the next wave early pays Cycles scaled to the countdown skipped. After the preview on purpose: paying for a decision whose terms are hidden is a slot machine, not a decision. Done: `CALL +8` in the preview's action row, one Cycle per second skipped, ~77 over a run against a curve that pays 409. **Open question the harness raised and this step did not settle**: with a scripted build order the call is free money - `rush` and `veteran` differ only in the call, and `rush` takes +77 and 1:15 off the clock with the same 5/5 core. Its real cost is reaction time, which a scripted player has infinitely much of. See the log.
- [x] Status bar + wave on demand (added mid-milestone 2026-08-24, not in the original seven) - the run's three numbers became three glyphs at the top center (heart, coin, `Lv 4`) instead of three labelled lines in the top-left, and the HUD became DOM so the **wave indicator could be a button**: tapping it opens the wave in the console, which is the only way to read one already on the board. Player's call, after playing the curve.
- [x] Verify - full playthrough of the ten-wave curve on desktop and phone, including a run that leans on 2x and a run that calls every wave early. Done: played and reported clean, which is what let v1.4 open without folding this forward.

Deliberately out of scope, with reasons, in [Run Structure](./Design/Run%20Structure.md): audio, new enemy behaviors, endless/high scores, a second map.


## v1.4: Portrait (chosen 2026-08-25)

What and why: [Portrait Layout](./Design/Portrait%20Layout.md) - the game is 16x9 and has only ever been held that way. Upright, the board floats in a tall black screen at a quarter of its area with 21px tiles, and the console is pinned to the bottom of the *window*, ~180px below the board it reports on. This is the debt the log accepted on 2026-08-23 ("in portrait there is no side band to tuck into [...] an orientation-dependent layout is a bigger change than the complaint asked for"), and the milestone that pays it.

**Reading at the top, controls at the bottom.** The 81px bands hold one 44px row each: the status glyphs stay centered up top with fullscreen and the orientation lock anchored right, and the bottom strip carries the build toggle and the console's collapsed header. A notched phone's 34px safe-area inset is why the bottom is one row and not two.

**The board rotates 90 degrees rather than shrinking.** Rotated, it fits at scale 4 and comes out 384x683 with 42px tiles - the same size as the landscape board, no loss at all. What that costs is the 326px of empty band that started the conversation: the rotated board eats it, leaving 81px on each side. So the board is maximal and **the chrome only fits because it collapses**, which is what steps 3 and 4 are about.

**v1.3's verify step closes first and is not folded in.** The precedent for folding owed QA forward (v1.1 into v1.2) applied because the interaction under test was about to be deleted; here it is not. The ten-wave curve is a gameplay verification in landscape, and nothing below changes what it measures.

Sequenced like the milestones before it: the manifest unlock first because the installed PWA cannot be held upright at all until it ships; the rotation next because every later step is positioned against the board it produces; then the two drawers, console before menu because the console's rule is the simpler of the two and the menu's needs a measured band to sit in; fullscreen before the lock because the lock API requires it.

- [x] Unlock the orientation - manifest `orientation: 'landscape'` becomes `'any'`. One line, no code, and the prerequisite for every step under it.
- [x] Rotate the board - when the window's aspect and the board's disagree, blit the world rotated 90 degrees and let `fitViewport` scale the rotated footprint. `clientToWorld` inverts the same transform, `boardRect` reports the rotated rect, and nothing else in the renderer or the sim knows it happened. **Counterclockwise**: spawn at the bottom, core at the top, because clockwise puts the core exactly where the console opens. The run's direction inverts against landscape, which is a reading decision verify can overturn. Checkpoint: landscape takes the branch zero times and is untouched. Done: one `rotated` flag on `Viewport`, an exact `setTransform` rather than `rotate(-PI/2)`, and `displayedSize()` swapping the axes for `boardRect`. **The predicate is not aspect disagreement**: it rotates when turning wins a bigger blit scale, tie going to leaving the board alone - same answer on a phone, and it makes the landscape checkpoint arithmetic rather than an argument. `tests/viewport.test.ts` gates both, plus the spec's own scale table.
- [x] Console anchors to the board - the console joins the status bar in parking against `boardRect()` instead of the window. Inverts their idiom rather than copying it: anchored by `top` and needing its own measured height, `top = min(boardBottom + gap, windowHeight - panelHeight - floor)`, with JS publishing `--panel-under-board` and `--panel-h` and CSS keeping the safe-area floor. A `ResizeObserver` on the panel covers collapse, mode switches and reflow with one hook. **The checkpoint is that landscape does not move a pixel.** Done: `panel.element` exposed for measuring, `placePanel()` publishing both numbers, a `ResizeObserver` on the console, and CSS `top: min(...)` with the safe-area floor where it already was. A 16x9 window lands on the floor and does not move; a letterboxed window - a 4:3 desktop, portrait - is where the board candidate wins, which is the whole point.
- [x] Build menu becomes a drawer - in portrait the left-edge column becomes a horizontal row of four 44px buttons with the cost on the label's own line (`FW 60`), opened and closed from a 44px button at the left end of the bottom strip, which it shares with the console's collapsed header. Closed by default is wrong and open by default does not fit, so it opens over the board's near edge like the console does, about 1.5 tiles. **The bands stay reserved for the collapsed state, so opening a drawer never re-scales the board.** Does not self-close after placing a tower; filed for verify. Done: one `turned` class on `body`, `applyLayout()` in `main.ts`, and CSS holding both layouts. **The drawer sits on the console's ceiling, not on the strip** - the spec left the collision between the two unresolved, and the tie-break is that picking a kind is what puts that kind's stats in the console, so a drawer covering the readout would hide the reason for opening it. Superseded after the first phone playthrough, on the player's call: the menu **stays a column in both orientations** and grows upward out of a toggle in the bottom-left, left of the console, over the board. The row shape lasted one milestone - a turned board leaves a 3px side band, but the column overlaps the board's edge either way, and one shape that collapses beats two that don't. **The toggle ships in landscape too**, which the spec had not asked for. `--menu-w` is reserved whether the menu is open or shut, so toggling it never moves the console.
- [x] Fullscreen - manifest `display: 'fullscreen'` (drops the Android nav bar in the installed app for free) plus `requestFullscreen()` from a button anchored right in the top band, beside the centered status glyphs. Feature-detected, silently absent on iOS. Worth more here than it would have been with a smaller board: the nav bar is ~48px of an 81px band. Done: `src/phone.ts`, `.top-tools` right-anchored against the new `--hud-row-top`. Renders on desktop too, where the API exists and the feature is real.
- [x] Orientation lock - a second top-band button pinning the phone to its current orientation via `screen.orientation.lock()`. After fullscreen because the API rejects without it on Android; rendered only where it exists, so desktop keeps today's header. Not a layout lock: the layout has no discrete portrait mode to switch, it is arithmetic off `boardRect()` either way. Done, with the API check **plus a coarse-pointer check**: desktop Chrome defines `lock()` and rejects every call, so the method alone would have rendered a button on every desktop that never worked once. A rejection dims the button for a moment rather than disabling it - pressing `FS` first is exactly what makes the next press work.
- [~] Verify - a run in each orientation on a physical phone, installed and in the browser. Three questions this milestone deliberately left to a playthrough: whether enemies climbing toward the core reads at all, whether the drawers open and close often enough to be worth the taps, and whether a sideways trace looks like a decision or like a mistake. First pass played and reported okay, with three changes that came back with it (menu shape, a toggle in landscape, a clearable build kind); the second pass, and the installed-app half, are still owed.

Deliberately out of scope, with reasons, in [Portrait Layout](./Design/Portrait%20Layout.md): a portrait-shaped map, re-authoring sprites for the rotated board, scaling the chrome with the board, a start screen.

Decided against during the spec, in order: **rotating the tower buttons' labels 90 degrees**, which was the original request, because with the board rotated the side band is 3px and no column fits it; **keeping the column on the board's left edge**, because drawn to scale a 206px toolbar covers a 192px board's full height and hides the spawn tile; and **dropping one scale step to 288x512** so nothing would ever overlap, because 42px tiles with dismissible chrome beat 32px tiles with permanent chrome.

## v1.5: Audio, part one - the desk and one track (chosen 2026-08-27)

What and why: [Audio](./Design/Audio.md) - the game has been silent through five milestones, and [Run Structure](./Design/Run%20Structure.md) deferred audio on the grounds that it is "the biggest single learning module left", which earns a milestone rather than a corner of one. The composer's first delivery arrived on 2026-08-27, and it is one mastered MP3 of 1:25 rather than the four WAV stems [Audio Brief](./Design/Audio%20Brief.md) asked for. So this milestone is deliberately **the desk, not the soundtrack**: build the mixing graph, put the one track through it, and leave the layer crossfades and the SFX to the two milestones after.

**The graph is what is actually being bought.** With one file, `<audio loop>` and three lines would make sound today; every decision below exists so that the layers and the SFX cost nothing structural when they arrive. This paragraph originally specified a `MediaElementSource`, to keep 84.7 seconds of stereo from costing 32 MB of float32 on a phone - the entire RAM budget the study note derived for four layers. Step 3 reversed it to a decoded buffer, because intro-then-loop needs `loopStart`, and paid the RAM back by going mono.

**No start screen.** The context unlocks on the first real gesture, with the audio button as the visible fallback. The study note argues audio forces a title screen; v1.4 already listed one as out of scope, and letting it in through the audio door is scope arriving sideways. Revisited in the SFX milestone, which is when silence before the first tap starts to matter.

Sequenced so the noisy steps come last: the file is prepared before anything plays it, the graph is built and checked **while the game is still silent**, and the PWA plumbing comes after there is a real file to route.

- [x] Encode and level - install ffmpeg, transcode to `.m4a` (AAC) with a `.webm` (Opus) alongside, measure integrated loudness and true peak, and settle the loop. Done, and the measurements moved three decisions rather than confirming them. The track is **120.000 BPM** with an 8.000s phrase, and it is not a loop but a shape: intro `[0, 20s)`, body `[20s, 76s)`, outro after. Loudness was **already on spec** at -18.4 LUFS - the assumption that it arrived mastered to streaming level was wrong - and only the true peak misses, at -0.1 against -6 dBTP. `MUSIC_DB` went **-12 to -4**, derived from the limiter threshold rather than guessed, because the peaks are 0.013% of samples and spending 6 dB on eleven milliseconds throws away the half that is right. Ships as `soundtrack.webm` (Opus mono 80k, **799 KB**) with an `.m4a` fallback; both decode to exactly 3,648,000 samples in Chrome, which is the portability MP3 cannot offer. The **sub-loop question to the composer is moot** - the body is the sub-loop, and it was already on the grid.
- [x] The graph, silent - `src/audio.ts`: context with `latencyHint: 'interactive'`, master to limiter to destination, `musicBus` and `sfxBus`, gain set in dB and applied with `setTargetAtTime`, unlock on first gesture, `visibilitychange` suspend/resume, `onstatechange` as the source of truth, `navigator.audioSession.type` where it exists. **The checkpoint is that the game is still silent** - same shape as v1.3's simulation extraction, where the checkpoint was that nothing changes. Done, with the checkpoint **restated**: the step as written said nothing else would import the module, and `main.ts` constructs it anyway, because a module nothing constructs never arms its unlock or sees a `visibilitychange` and the checkpoint collapses to "it compiles". Constructed and silent is the stronger claim, and the one verified in a browser: `running` after a real click, and an `AnalyserNode` on the music bus reading a peak of exactly 0. The gesture listeners **arm and disarm off `statechange`** rather than firing `once` - a spent `once` listener strands the game silent after Safari's `interrupted` state. `dbToGain` is the one pure function and is gated in `tests/audio.test.ts`. **Amended during step 3**: the chain ended in a `DynamicsCompressorNode` and now ends in a `WaveShaperNode` curve, because the compressor was measured adding 1.71 dB of implicit makeup gain at every level including 21 dB below its own threshold - a node that raises the peak is not the net it was there to be.
- [x] The track on the bus - `fetch` plus `decodeAudioData` into an `AudioBufferSourceNode` on `musicBus`, fetched lazily after the first gesture so it never sits in front of the first frame. **Reversed from the media element this step originally specified**: the intro-then-loop structure needs `loopStart`/`loopEnd`, which an `<audio>` element does not have, so the buffer is a requirement of the music rather than a preference. Done in `src/music.ts`, kept separate from the desk because it is the file that becomes the layer crossfader. `loop = true`, `loopStart = 20`, `loopEnd = 76` is the whole mechanism, and rendering the seam offline confirms it: the loop jumps from the buffer's 76s sample to its 20s sample exactly, and the step across the join is **0.02 against a 0.22 maximum elsewhere in the same music** - five times smaller than the loudest ordinary transition, so there is no click to hear. Nothing is fetched before the first gesture, and nothing at all while muted. Two things the step did not anticipate: the trim moved again, **-4 to -7**, once the peak was measured on the decode rather than the file (lossy decoding overshoots, and this one lands at +2.52 dBFS); and the ceiling replaced the compressor, which sent step 2 back for an amendment.
- [x] The control - a third button in the top band beside `FS` and `LOCK`, same bracketed `[x]`/`[ ]` vocabulary, persisted in `localStorage` (the project's first). Doubles as the re-arm for Safari's `interrupted` state, which is the cheap answer to a context that needs a fresh gesture to come back. Closes "Settings (sound toggle) once audio exists" from [Idea Bank](./Idea%20Bank/Idea%20Bank.md). Done, and the label became a **pixel-drawn music note** rather than the `SND` it shipped with for an hour - the one control in the row that has a symbol everyone knows, where the other two do not. The heart's SVG builder moved out of `hud.ts` into `glyph.ts` to serve both. Sized `16px` and not in ems, because eight source rows into sixteen device pixels is exactly 2x: at the 1.25em it started as the scale was 1.875, the one-pixel beam rasterised two pixels thick and the stems alternated full and half coverage, which is the board renderer's integer-scaling rule arriving in the chrome. **`phone.ts` became `top-tools.ts` in the same step**, and not only for the label: fullscreen and the lock are both feature-detected, neither exists on an iPhone, and the old module returned before building the row - which would have left no sound button on the one platform where it is load-bearing. `[x]` means `running && !muted`, a stricter claim than "not muted", so a suspended or interrupted context reads dark rather than lying; a press then unmutes *and* resumes, which is what makes the button its own repair. Falls out of that: on a fresh load it reads `[ ]` and is **the nearest thing the game has to a start affordance**, in a milestone that refused to add a start screen. A muted run never fetches the track, so the toggle also saves 799 KB rather than only remembering a preference. **Then the row became a drawer**, on the player's call, because three buttons in a right-anchored row covered the centered wave indicator: the glyphs run 112-278 on the reference phone and three buttons put the row's left edge at 238, over 27 of `Lv N`'s 35 pixels. Collapsing behind a gear fixes it at the root rather than by moving anything - shut, the band's footprint is one 44px button on every device no matter which controls exist, so the collision cannot come back the next time something is added.
- [x] Swap in the WAV master - the delivery [Audio Brief](./Design/Audio%20Brief.md) asked for in the first place, which arrived 2026-08-28 (84.58s, 48kHz/24-bit stereo, 23.3 MB). Not on the original plan for this milestone, and it earns a step rather than a footnote because **it is a different master, not the MP3's source**: same piece and same edit points - the body still starts at 19.99s and decays from 76.03s, so `loopStart`/`loopEnd` did not move - but envelope correlation between the renders is 0.73 and sample correlation only 0.43, so every measurement had to be taken again. ## v1.6: The run, part two - enemies and pressure (chosen 2026-08-30)

What and why: [Difficulty](./Idea%20Bank/Difficulty.md) - player feedback says the ten-wave curve is too easy, and the note that came out of checking that feedback against the harness gave four reasons. Three of them are what this milestone picks up: difficulty has exactly one knob and `hpScale` is the wrong one, nothing accumulates against the player because the countdown starts when the board *clears*, and six enemy kinds only ask two distinct questions - Ransomware splits, and the Zero-Day is immune to AES Turrets, while the other four are HP and speed variations on "shoot it". The fourth reason, that the economy stops binding halfway, is deliberately left alone below.

**Three objectives, chosen by the player**: new enemy kinds, a longer curve with more than one scaling axis, and overlapping waves with a way to call the next one from the board. The steps below are those three plus the two the project's own rules add - a refactor before the kinds land in it, and an instrument before the curve is retuned without one. The instrument is half of what it was first drafted as: the margin bisect stays, the Overclock policy was cut on the player's call.

Sequenced like the milestones before it: the trait refactor first because a table is cheaper to change while it holds six things than while it holds nine, the kinds landing into that table rather than beside it, the shape change before the longer curve because tuning waves 11-15 against a shape about to be replaced tunes nothing, the affordance after the shape because it is the affordance for a decision the shape creates, and the instrument between authoring the curve and tuning it. That last one is late rather than first, which reverses the first draft of this plan and is the one place the order is a compromise instead of an argument.

- [x] One trait table - `SPLIT_ON_DEATH` and `IMMUNE_TO` are two `Partial<Record<EnemyKind, ...>>` tables in `enemy.ts`, each with its own accessor pair, and `panel.ts` hand-renders one row per behavior. A third behavior would be a third table, a third accessor and a third branch, which is the shape that stops being fine at exactly the moment this milestone starts adding behaviors. Fold them into one per-kind trait record read through one function, with the panel rendering rows off the traits rather than off a list of ifs. **The checkpoint is that nothing changes** - same six kinds, same panel readings, same tests passing untouched. Same shape as v1.3's simulation extraction and v1.5's silent graph, and the reason it comes before the kinds rather than after them. Done: one `EnemyTraits` record with an optional field per behavior, one `enemyTraits(kind)` accessor that never returns null, and a `TRAIT_ROWS` table in `panel.ts` that turns traits into console rows. `isImmuneTo` survives as its own predicate instead of being read off the traits at the call site, because its caller is the targeting loop and `isImmuneTo(enemy.kind, tower.kind)` is what that loop means. **The checkpoint held in the strongest form available**: `npm test` passes 27 of 27 with no assertion touched and only three call sites renamed, and `npm run balance` prints the seven loadouts identical line for line to the table [Difficulty](./Idea%20Bank/Difficulty.md) recorded on 2026-08-28 - same verdict, same core, same leaks, same Cycles, same clock. And what the old shape cost is clearer now that it is gone than it was while it stood: the row counter in `renderEnemy` was advanced by hand inside every branch, so a behavior added without remembering to advance it would have quietly overwritten the row above.
- [x] New enemy kinds - the study the objective asked for came back with a result worth writing down, because it is the opposite of what a codebase this age usually gives: **outside `enemy.ts`, `wave.ts` and `scripts/gen-sprites.mjs`, no code in the project names an enemy kind.** The renderer, the panel, the sim and the harness all read `enemy.kind` generically. So a kind costs a row of stats, a sprite, and a place in the curve, and the refactor debt is in the behaviors rather than in the kinds. The one hole is that `enemy.kind as SpriteName` is cast in three places in `render.ts` and nothing checks the sprite exists, so a kind added without art fails at draw time; a startup gate or a union that makes the cast unnecessary closes it. **Three kinds chosen, and specced in [Roster](./Design/Roster.md)** rather than here, which is a note this milestone created because the question a kind asks is the part that does not change when the retune moves its numbers: **BEACON**, which the slow auras cannot touch and which punishes the aura build the way the Zero-Day punishes the all-turret build; **PACKER**, flat damage reduction per hit, whose answer is a Firewall Node at tier 2 as much as it is an AES Turret, so it prices the tier ladder in the late run where [Difficulty](./Idea%20Bank/Difficulty.md) says the player stops choosing; and **ROOTKIT**, untargetable unless it is inside an IDS Scanner's radius, which resurrects the "reveals stealth" ability cut on 2026-07-12 for the reason recorded then - no stealth enemies existed, so it had nothing to do. Two decisions the spec settles because they cost nothing now and a rewrite later: the BEACON's trait is **fixed movement**, living where speed is consumed rather than where each slow is produced, which also forces the wave speed axis two steps down to be applied at birth like `hpScale` rather than as a per-tick multiplier - otherwise the kind would silently opt out of the difficulty curve; and the PACKER's damage floor is **zero, not one**, because a minimum of one keeps every board working and turns armor into a tax instead of a question. Build order: BEACON, then PACKER, then ROOTKIT, which is ascending order of how much of the game each one touches - a field, then a field and a formula, then a field, a targeting rule, a tower ability and a render tell. **BEACON is in** (2026-08-30): the trait, the stats, a 14x14 sprite, and `tests/enemy.test.ts`, which is a new file because the roster now has rules of its own to gate - what a kind *is*, as against `tests/wave.test.ts`, which gates where it shows up. One of those gates is the hole this step named: **every kind must have a sprite**, which closes the `enemy.kind as SpriteName` cast for one assertion instead of a startup check on a hot path. **PACKER is in** the same day: `armor` on the traits and a `damageTaken(kind, amount)` that `stepGame` calls at the one place a projectile lands, so towers keep declaring what they deal and stay ignorant of what survives it. **ROOTKIT closes the step**, and it is the only one that changed a tower: `reveals` on the IDS Scanner, tier-independent so that "did you buy a Scanner" cannot degrade into "did you buy enough Scanner"; one aura pass that now answers both of its questions at once, since slow and reveal ask the same thing about the same pairs; `isHidden` read by `findTarget` and by the renderer, so the rule has one definition and the ghosting cannot disagree with the targeting; and a `REVEALS STEALTH` row on the Scanner in both the tower and build panels, because the console exists so a piece says what it does before it is paid for and this is the one ability that is worthless until the run needs it. None of the three has a wave yet - placing three new kinds in a curve that is already ten waves of tuned shape is the job of the two steps below, and the checkpoint that says so is that `npm run balance` still prints the seven loadouts unmoved after both.
- [x] Overlapping waves - the countdown starts when a wave finishes *spawning* rather than when the board clears. The largest single change available: it makes concurrency the difficulty axis instead of HP, and it turns a leak into a debt, because the stragglers you failed to kill are still walking when the next wave opens. Smaller in the sim than it sounds - `stepSpawner` goes `spawning` to `countdown` directly and `waiting-clear` survives only to close the run - and it comes with a reading the plan did not ask for: `nextWavePreview` returns null outside `countdown`, so today the next wave cannot be read during the tail of the current one, and after this it can, which is exactly the information the next step's decision needs. It also finally gives the early call the mechanical cost v1.3 recorded it as missing. Done, and the harness answered v1.3's open question outright: **`rush` went from the best row in the table to a loss.** It was 5/5 with zero leaks and 486 Cycles earned - the same board as `veteran` plus the call - and it now breaches the core, 0/5 with leaks at waves 4 and 10 and a peak of 17 enemies at the boss, in a run 0:54 long. Calling every wave the instant it can be called is no longer free money with a shorter clock; it is a way to lose. **And the same table qualifies it, which is the more useful half**: `veteran` is unchanged at 5/5 with zero leaks and peaks between 1 and 8. For a patient board the gap between the last spawn and a clear board was only about 3.5 seconds a wave, so overlap deletes 35 seconds of dead time over a run and adds almost no pressure to a player who does not ask for it. That is arguably the right shape - difficulty the player opts into - but it means **"too easy" for the patient player is still entirely the longer curve and the retune to answer**, and this step should not be credited with it.
- [x] Call the wave from the spawn port - the port blinks with `>>` inside it while a call is available, and tapping it calls the wave. Today the only way to call early is the console's `CALL +8` row, which means opening a drawer to take an action about a thing on the board. **The blink is sprite frames, not a new mechanism**, which is the player's correction to a first draft of this step that priced it too high: `drawSprite` already takes a frame index and wraps it modulo the frame count, `spawnPort` simply has one frame today, and `drawEnemies` already runs a frame clock off `timeMs`. Nor does the port have to leave `prerenderBoard`, as that draft claimed - `main.ts` blits the prerendered board every frame anyway, so the animated port draws over the static one in the dynamic layer exactly like an enemy does. An overlay can only **add** pixels, and **the blink is the two arrows alone, lighting and going dark over a port that never changes** - the player's call, and it lands on the additive side by construction, so the port keeps its place in the prerender and nothing about the static board moves. That also makes the smallest form the right one: the `>>` is its own small sprite drawn over the port on the frame clock while a call is available, rather than a second frame of `spawnPort`, since the port pixels underneath are already on screen and redrawing them buys nothing. The variant this rules out is a blink that dims the whole port, which is the one that would have cost the port its place in the prerender. The tap needs a branch in `pointerdown`, which is free today because the spawn tile is path and never buildable. **Three affordances by the end, with different jobs**: the console body keeps `CALL +8`, the only surface where the bonus number fits; the port is the fast path on the board; and a `>>` in the console header, added on the player's call, covers the state the run is actually played in - collapsed, watching the board, where reaching `CALL +8` means opening a panel over the board you would be calling the wave onto. **The rule that decides which of them confirms is where it is**: a button in the chrome is a thing the player went to press and acts on one tap, and a tile on the board is a thing their finger was already over and takes two. **The port is a two-state control, on the player's design** (2026-08-30): by default it marks the time to the next wave, one tap turns it into the arrows, and a second tap calls. Armed, **the arrows replace the port's content rather than sitting on it** - the two outer rings stay so it is the same object in the same place, and everything inside becomes one big `>>` in the port's own green. That reverses the earlier "only adds pixels" constraint into a stronger one: the armed sprite must be opaque everywhere the plain one is, because the plain port is in the prerendered board and a transparent pixel would be the old port showing through the new one. `tests/sprites.test.ts` gates it pixel by pixel. That is a confirm step, and it earns one - the port sits on the board where the player is already pointing, so a stray tap would otherwise spend a decision that cannot be taken back. It also answers this step's open question rather than living beside it: the default state is a clock rather than a blink, so a board where a call is available almost all the time is not a board flashing at you almost all the time. The tension worth naming is that v1.2 deleted an arm-then-act mode (`overclockArmed`) for being a keyboard idiom in a phone game; the difference is that that mode lived off-target, over the whole board, and this one lives on the control itself, which is how every confirm on a phone works. Done, and one thing the spec did not anticipate came out of building it. The pips are one per whole second, which is the number the console already prints as `IN 8s` and the number the early call already pays - and **that rounding was being done independently in two places before this step added a third**. It is now one `countdownSeconds` in `wave.ts` that all three call, gated by a test, which is what makes the docblock's claim true rather than aspirational. The port is a control **only while there is a wave to call**; otherwise a tap on that tile falls through to whatever is standing on it, which keeps a stray enemy from making the port unreachable and keeps the port from swallowing a tap meant for the enemy. The chevrons are **screen-locked and always point right**, reversed on the player's call after seeing it run: the first cut pointed them along the trace and let the board's rotation carry them, which is right as a compass and wrong as a button. `>>` is read as "go", a direction learned from every media control there is, and a `>>` pointing up the screen because the phone is upright is a symbol asking to be re-parsed. The rotation maps world +y to screen +x, so one quarter turn cancels it exactly - and being a quarter turn, the pixels stay on their integer grid. The blink is 700ms rather than the 220ms sprite clock, where it reads as a fault rather than as an invitation. **Verified by the player on 2026-08-30**, in the browser rather than through the extension, which was disconnected again - the third time this project has recorded it. The two-tap interaction and the pip ring came back fine. **The blink did not, and the correction is the player's**: alternating the armed sprite with the plain port underneath made the arrows read as *disappearing*, which is the wrong verb for a symbol that means "go". So the arrows no longer go out - the armed sprite is drawn on every frame while armed and carries two frames of its own, with the light marching from the first chevron to the second and the unlit one drawn in the port's dark green rather than removed. The rate went the other way with it, 700ms to 380ms, and that direction is the argument rather than a side effect: a symbol going dark has to be slow or it reads as a fault, while a light travelling along an arrow has to be quick or it reads as two blinks instead of one movement. It also strengthens the invariant the step was built around - there is no longer any frame in which the armed port is not painted over the prerendered one at all. Open question for the step, and narrowed rather than answered by the arrows-only decision: after overlapping waves the call is available for most of the run, so arrows that blink whenever it is callable are arrows that blink nearly always, and something on the board pulsing continuously is either an invitation or a nag depending on how often the player was going to take it.
- [x] More waves, and a second scaling axis - the curve grows past ten, and `hpScale` stops being alone. **Speed** is the other half of the same idea and deliberately attacks something else: it shortens time-in-range, so it presses coverage and placement rather than DPS, and it makes the IDS Scanner and Honeypot slow auras matter more the deeper the run goes. **Armor** arrives with the kind that carries it and can be declared per wave for the same reason. Two questions the step has to answer rather than drift into: whether the Zero-Day moves to the new end or the run gets a second act with a second boss, which [Difficulty](./Idea%20Bank/Difficulty.md) filed as "fifteen waves, each kind reintroduced carrying a modifier"; and whether the payout grows with the length, which it must not do naively - the note's fourth reason is that a winning run already ends with 164 to 241 Cycles unspent, and five more waves at the current rates make that worse rather than better. Done, and both questions came back answered by arithmetic rather than by taste.

  **The shape**: fifteen waves in two acts. The Zero-Day moves to the new end and the run gets a second *act* rather than a second boss - a second boss would have wanted a fourth new kind, and this milestone's kinds are chosen and built. Act one is 1-8, the ten-wave curve minus its last two waves, kept as it stood because it is the half the player never called easy; its climax is the old sniffer-and-Trojan crunch at 8. Act two is 9-15, and it alternates: BEACON alone at 9, PACKER alone at 11, ROOTKIT alone at 13, each followed by the wave that puts it back on the board under load, then the boss. **The two acts scale on different axes**, which is the point of there being two - act one ramps `hpScale` and asks whether the guns are big enough, act two ramps `speedScale` on top and asks whether they cover enough trace, and that second question is answered with placement rather than with another upgrade. The old wave 9 crunch is gone; wave 14 takes over its job.

  **The axis** is born in `createEnemy` alongside `hpScale`, exactly as [Roster](./Design/Roster.md) demanded a step early, and `tests/enemy.test.ts` now gates the trap it predicted: a BEACON born on a 1.3x wave and slowed by an aura in the same breath comes out at 1.3x. The plumbing is **one `WaveScale` record rather than a parameter per axis**, for the same reason step 1 folded two behavior tables into one - `hpScale` alone was already a number threaded through an accessor, a parameter, a field on `Enemy` and the split that inherits it, and each of those would have grown a twin. **Per-wave armor was considered and refused**: a wave that hands everything armor 1 makes every kind ask the PACKER's question, and a question every kind asks is one no kind owns. Speed scaling is a change of tempo; armor is a change of what counts as an answer.

  **The payout could not stay flat by shape, and that is the finding.** The ladder costs 570 to top out and did not get longer when the run did. Fifteen waves of this shape at the ten-wave bounty rates pay 580 on their own - a purse of 680 against a 570 ceiling - and no arrangement of counts fixes it, because even *three* extra waves overshoot. So the bounty table was re-derived rather than nudged: **a kind is worth its base HP**, with a premium only for the ROOTKIT, which costs a tower purchase before it can be shot at all. The old table was 1.25x HP with a 2x on both the Packet Sniffer and the ROOTKIT, and the Sniffer's premium is what went - at 1 HP it is the cheapest kill in the game, and paying double for it made 53 sniffers a quarter of the whole purse. The consequence is a property the curve wanted anyway: **the one body used to make a wave crowded is the one that barely pays**, so act two can crowd the board without inflating the economy. Purse lands at 526 against the 570 ceiling. **This is a deviation from the plan's split** - bounties were meant to be the retune's - and the reason it could not wait is that the economy gate is computed from the curve, so the curve cannot land while it is red. What the retune keeps is the *difficulty* numbers, which is what the margin instrument below is built to measure.

  **One lever came out of the harness and is worth carrying forward**: the first cut of act two peaked at *one* enemy on each of the three teaching waves and `veteran` finished 5/5 without a scratch, because five enemies 1.4 seconds apart against a board that kills each in under a second is a queue, not a wave. Tightening the spawn intervals fixed it, and **the interval is the only lever that adds pressure without adding bounty** - counts are the economy, scale is capped by what the retune can afford, and the interval is free.

  **What the harness says now**: `veteran` finishes 4/5, **its first leak in the project's history**, and the leak lands on wave 10 - the BEACON mix, the wave built to punish exactly the aura build `veteran` leans on. `rush` breaches the core again, so the reading step 3 produced survives a curve half again as long. `focused` drops from the second-best row to a breach, and the reason is the wall [Roster](./Design/Roster.md) predicted rather than a tuning slip: it never buys an IDS Scanner, so the ROOTKIT is a kind it cannot answer at any tier. And the fourth reason in [Difficulty](./Idea%20Bank/Difficulty.md) - the economy that stops binding halfway - is most of the way fixed as a side effect and without an economy sink: `veteran` ends on 62 banked where it used to end on 164. The declared loadouts were extended for `veteran` and `rush` only, because a build order that stops at wave 9 measures act two against a board that quit, and that reads as a curve that got hard when what got hard was the yardstick.
- [x] Margin, not verdict - a run-wide HP multiplier on `GameState`, which `runBalance` bisects to report the multiplier at which each layout takes its first leak and the one at which it loses. That is a signature change to `createGameState` rather than a flag, because `stepSpawner` and `waveScale` read the module-level `waves` directly and there is no curve to inject. It sits between authoring the longer curve and tuning it: the step above decides the shape, and this is what lets the step below pick numbers for it instead of guessing them. **Overclock in the sim was cut from this step**, on the player's call, and the consequence is worth carrying rather than forgetting: `triggerOverclock` stays called from `main.ts` and nowhere else, so every row the harness prints remains a floor on player capability rather than a reading of it, and every margin reported here is conservative by however much the ability is worth in the moments the curve is trying to be hard. Done, and the shape held: `hpScale` on `GameState`, defaulted so the game reads exactly as it did, composed with the wave's own scale in one `runScale` that returns the wave's record untouched at 1x. `createGameState` grew an options bag rather than a second argument, which is the smallest signature change that leaves every caller in the game alone.

  Two things came out of building it that the plan did not have. **The bisect runs in log space**, because the answer is a multiplier and a percent matters equally at 0.5x and at 4x - a linear bisect spends most of its steps resolving the top octave nobody reads. Nine halvings of five octaves puts the answer inside a percent, and the whole seven-layout table costs 2.6 seconds.

  And **the number is worthless without a wave number beside it**, which the first reading proved rather than argued. `veteran` came back as "loses at 1.17x", which reads as a curve with no headroom left. It was nothing of the kind: it died at **wave 2**. A run-wide multiplier finds the weakest link in a run, and the weakest link was the opening - two tier-1 Firewall Nodes and a Honeypot, which is what 100 Cycles buys, against a Worm whose 3 HP rounds to 4 the moment the multiplier passes 1.167. So the reported margin was a rounding cliff on the smallest enemy in the game, in the one stretch of the run where the player has not yet made a decision, and every bit of tuning aimed at act two would have been invisible inside it. `MarginReport` gained `firstLeakWave` and `lossWave` - the wave that drew blood, and the wave that took the last core HP, which are deliberately different questions. The gates in `tests/balance.test.ts` check the instrument rather than the reading, as that file's docblock demands: the scalar is off by default and off is byte-identical, and the reported threshold is bracketed from both sides, so a bisect cannot return a number nothing actually happens at.
- [x] Retune, and the gates that encode the old shape - re-derive the curve against the new shape with the instrument from step 1, aiming at a **margin band** rather than at a verdict. ## v1.7: Before the run - the shell (chosen 2026-08-31)

## v1.8: The second board (chosen 2026-09-12)

What and why: v1.7 built the before and left one thing a line of data away - `runs.ts` reads a list, and the shell prints names instead of a start button the moment there is more than one to print. This is the **first content this project adds rather than the first system**, and the reason it is next is the one the 08-31 session argued: a second map had nowhere to be chosen, and now it has.

**What the second board asks, settled here.** A map that is a different squiggle is the same problem drawn differently, so this one has an axis: **the trace doubles back on itself**, so a tower can be placed where it covers two stretches of it at once. That turns the question from *how many* into *where* - which is the axis act two already leans on with `speedScale`, and the one the console's range circle exists to make readable. It is also not a new idea so much as an old hint made the point: level 1's legs already meet at their turns, and `VETERAN_BUILDS` in `balance.ts` has been quietly exploiting that since v1.3 with two Firewall Nodes on row 3.

*Planned as a horizontal fold with the legs two rows apart. Drawn three times before it shipped, and the two redraws were both the player's, both made from an ASCII drawing rather than from a number - see step 4. The shipped board is an **S**: in and out at the same height on opposite edges, doubling back on the vertical axis, with the inside of each bend as the board's good real estate.*

Same **16x9 grid**, deliberately. The shape carries the difference, the size does not, and that keeps the viewport debt out of scope: `createViewport` is sized once from the boot map's `cols`/`rows`, and a differently-sized board is the only thing that would force it to be rebuilt rather than re-fitted (noted in `main.ts`, and still true after this milestone).

**The one thing the fold costs, named before it is measured.** On a 16-wide board any fold-back crosses the horizontal two or three times instead of once, so the trace goes from level 1's 19 tiles to somewhere in the high twenties. With a fixed curve, path length *is* difficulty - 40% more trace is 40% more time in range - so **the second board is easier than the first unless something says otherwise**, and nobody asked for that. This project does not settle that kind of question by feel: `npm run balance` and `runMargin` exist for exactly this, and pointing them at the new board is a step rather than a footnote.

> **Measured, and wrong.** Left standing above because it is what the milestone was planned against, and step 4 below is what it cost. Path length is *not* difficulty: on the shipped board, the same Cycles spent two tiles off the bends first leak at 0.64x against level 1's 0.65x - the same board, on a trace eight tiles longer, made no harder by the length. Trace nothing covers is not time in range, it is enemies walking for free.
>
> The proof arrived three times over, once per drawing, and the cleanest was the middle pair: **two boards of exactly 29 tiles, 0.36x apart** (a fold two rows deep at 1.15x, a corner sweep four rows deep at 0.79x). Same length, same curve, different board. The one that shipped is *shorter* than both at 27 and lands between them at 0.96x. What a player pays for is coverage.
>
> Some cost is unavoidable in any case: level 1's trace is already a minimal path from edge to edge, so any detour is paid for twice and there is no second board at 19.

Deliberately out of scope: **a second wave curve.** The curve is global and stays that way - if this board needs different pressure, the answer is its shape, not a second table, because two curves would double every tuning question the harness answers and would make a record's curve hash ambiguous the same week it stops being ambiguous. ## v1.9: The run as data (chosen 2026-09-12)

What and why: the top of the sequence the [Idea Bank](./Idea%20Bank/Idea%20Bank.md) ranked on 2026-09-12, and it is there because three items turned out to be one instrument. [Difficulty](./Idea%20Bank/Difficulty.md) has said since 2026-08-28 that the harness and the players are not disagreeing, they are **measuring different things** - and v1.8 just spent a session proving how sharp that edge is. Every number that milestone printed came from a script that never fires Overclock, never sells, and never changes its mind, against a board whose whole thesis is a placement decision. The reading was still worth having. But the thing it could not say is what a *person* does on that board, and no amount of tuning the instrument fixes an instrument that is measuring the wrong runner.

**The run becomes data, and the same data answers three questions.** A seed plus an input log is a whole run in a few bytes: it makes a bug report from a phone that is not here reproducible, it turns determinism from a claim into a test, and it lets a real human run be played back *inside* `balance.ts` - which closes the harness-versus-player gap literally rather than by approximation. The post-run report is the same measurement pointed at the player instead of at the log.

**The determinism gate goes first, and it is not a formality.** The whole milestone rests on the game and the harness being one simulation. Today that is a claim: `stepGame` is shared and `GameLoop` is a fixed-timestep accumulator that always calls `update(TICK_MS)`, so the timestep is not where they could have drifted - but `hooks` is, the game's particle burst is the only thing in the project that reaches `Math.random()`, and nothing has ever asserted that a run stepped by the game equals the same run stepped by the harness. If they diverged in silence, every number v1.3, v1.6 and v1.8 printed is wrong, and the gate is the cheapest possible place to find that out.

**Scoped like a record, for the reason v1.7 and v1.8 both learned.** A replay is a statement about a curve *and* a board: retune `waves` and every stored log is about another game; change the map and it is about another board. `CURVE_ID` and `RunDescriptor.id` already exist and already mean exactly this, so a replay carries both and a mismatch reads as "not a replay of this game" rather than as a corrupt file. This is the third time that lesson has been paid for and the first time it costs nothing.

Deliberately out of scope: **sharing a replay anywhere.** Handing a run to someone else needs a server, and a backend is the one item the Idea Bank keeps calling a different project rather than a next step - static-on-Pages is what makes the deploy a push and the game work offline. A log that can be copied out as text is as far as this goes. Also out: a replay *viewer* beyond what the report already draws, and the adaptive layout, which the ranking demoted from a measurement to a regression gate and which belongs to sequence item 3.

- [x] The determinism gate - one simulation, asserted. A `GameState` stepped N times by the harness and the same state stepped N times through the game's own path produce identical states, hooks and all. The claim under test is not "the sim is deterministic" - `tests/game.test.ts` has covered that since v1.3 - but the one nobody has written down: **that the thing the player plays and the thing the harness measures are the same thing**. Where it is most likely to be false is the hook seam, since the particle burst is the only `Math.random()` in the project and the game passes a hook the harness does not.

  **Done, and the answer is yes** - which is the answer this milestone needed and not the one that would have been most interesting. `tests/game-loop.test.ts` is new, and `game-loop.ts` had no tests at all before it: the module every played tick passes through was the one module in the simulation nobody had gated. `requestAnimationFrame` and `performance.now()` are stubbed and the clock is driven by hand, the same idiom as the `localStorage` stub in `records.test.ts`, and it buys more than portability - a hand-driven clock serves frame times no real machine would, which is exactly where a fixed timestep either holds or does not.

  Six gates. Five are about the loop: every tick is `TICK_MS` whatever the frames were; the remainder is carried, so ragged frames and even ones of the same total run the same simulation; a 60-second stall is clamped to 250ms rather than caught up on, which is the one place the loop deliberately drops simulated time; **speed scales how many ticks run and never how big one is**, which is the whole of what makes the fastest-clear record mean anything; and a pause banks no time to spend on resume.

  The sixth is the gate itself: one state driven through `GameLoop` on ragged frames with `main.ts`'s hooks, another driven by a plain `stepGame` loop with none, and **the whole state compared** after the same tick count rather than the four scalars the v1.3 hook test settled for. Particles are the one exception, and it is checked rather than assumed - the hook call is counted, so a passing comparison cannot be one where nothing happened.

  **A debt found on the way, and it is this milestone's own subject one floor up**: `tsconfig.json` has `"include": ["src"]`, so `tests/` and `scripts/` are never type-checked. Nothing makes a test agree with the source it tests, which is how a `createEnemy('worm', 1)` - a `WaveScale` argument given a number - ran in this very session and failed as a wrong assertion instead of as a type error. Not fixed here: it wants `@types/node` in a project that has kept itself to three devDependencies, and that is a stack decision rather than a step.
- [x] The run as a log - record what the player did, as ticks and actions: place, upgrade, sell, call early, Overclock, and the tick each happened on. Not wall-clock and not frames - the tick, because that is the only clock both simulations share. The log plus the descriptor (board, curve) is the run. What this step has to decide rather than assume: whether the log is written continuously or assembled at the end, which is the same question save/resume answers from the other side, and whether a log is kept at all when nothing asks for one.

  **Done, and both open questions were decided rather than assumed.**

  **Written continuously, and what is assembled at the end is only the envelope.** Reconstructing a log from the finished state was refused for the reason v1.8 deleted its last-run key: a second account of what happened is a second thing that can be wrong about it. Every action is already a function in `game.ts` that returns whether it took effect, so recording is one line at the point of the fact. Board, curve and length are sealed at the end because those are facts *about* the run rather than events *in* it - and `ticks` has to be one of them, since the actions cannot imply it: the last wave is walked and killed with nothing left to press, so a replay stopping at the last logged action would stop before the verdict it exists to reproduce.

  **The action logs itself, because only the action knows whether it happened.** A tap on a taken tile and a tap with no Cycles both reach `placeTower`, and neither is an event in the run. Logging from the caller would file the intent, and the replay would then be reproducing a run nobody played. The gate for that is the refusals: six rejected taps, log untouched.

  **The tick became state, and that deleted two counters.** `GameState.tick` is the clock both simulations share, and `runMs` in `main.ts` (summing a `dtMs` that is always `TICK_MS`) and `runBalance`'s local `ticks` were the same number kept by hand in two more places. The fastest-clear record is now `run.tick * TICK_MS` read off the run, and so is the harness's `durationMs`. One counter, and it is the one stamped on every log entry.

  **Overclock got a door that knows about the run, and it is the one step 4 was waiting for.** `triggerOverclock` takes a tower and knows nothing about a run, which was right while its only caller was a tap. But it is an action a player takes, so it is an action a replay has to reproduce: `overclockTower(state, tower)` logs when it fires. The caveat under every margin table since v1.6 - no reading has ever used Overclock - stops being a missing entry point.

  **Kept while it is played, not kept after.** Recording is what makes a log available to whatever finally asks, and a run is tens of entries. Persisting is a different decision with its own questions (which runs, how many, what happens when the curve moves) and nothing has asked them yet. The log is sealed on the tick the run ends - the same place the record is filed, and for the same reason - and held in memory. Today a DEV `runLog()` reads it; step 5 is what reads it next.

  **Text and not JSON**: every line is `<tick> <verb> ...`, because the whole value of this artifact is fitting in a bug report typed on a phone. The parser is strict on purpose - header, verb, tower kind, enemy kind, whole-number tile, tick order, exactly one ending and nothing after it - and returns `null` rather than a partial log, because a log that reads with one line missing replays into a different run and reports the difference as a determinism bug.

  **Then the first real run was played, and it moved the format.** Twenty-six actions on RECURSION 02 in 2:31, and three things came out of it that no synthetic log would have said. The last action is at tick 8141 of 9081 - **fifteen seconds of run after the last tap**, the final wave walked and killed with nothing left to press, which is the field `ticks` exists for and now confirmed rather than reasoned. **Zero sells and zero Overclocks in a whole run**, which is a reading about the player that the project has never had a way to take, and it lands right before the step that measures what Overclock is worth. And the one that changed the code: **the envelope had no verdict**, so a log pasted from a phone - the case this milestone actually named - had nothing for a replay to disagree with. A replay nothing can falsify is not a gate.

  So the log grew its output half, and the player's own suggestion is what completed it: **record the enemies that walked through**. Format is now `ice-breaker/2`. Actions are input, what a replay *does*; leaks and the ending are output, what it is *checked against* - and the finer that half is, the more the gate catches, because a replay that reaches the same core HP by leaking a different wave passes a verdict and fails this. A leak is stored as **an enemy and not a hit point**, which is the one thing only the simulation can say at the moment it happens: every other leak count in the project is the core's lost HP, and a Zero-Day takes three of them by itself. The ending line carries status, core HP, Cycles and wave, and its tick is the run's length, so the header went back to being identity alone. The two halves print merged into one timeline, leaks ahead of actions on a shared tick - not a tie-break but the truth, since a leak happens during a tick and nothing can be tapped mid-step.

  This is not the post-run report arriving early: the log *records* leak attribution, and what that step owes is a player reading it. This feeds it rather than jumps it.

  **And then a second run came back flawless, which is the strongest reading this project has taken from a single game.** `won 5 64 15` in 2:08 on RECURSION 02, not one `leak` line - kept as `tests/runs/recursion-02-flawless.run`, because it is the only human run that exists and it cannot be regenerated. Eight towers inside a 3x3 block, x 4-6 and y 5-7, with seven upgrades on top; `VETERAN_BUILDS_2` opens in the near elbow and **moves to the far one at wave 9**, on the argument written in the file itself - "the half of the run the opening cannot reach". The human run never went there. Side by side on the same curve and board: `veteran` clears in 3:18 with 4 core, 1 leak and 62 banked; this clears in 2:08 with 5 core, 0 leaks and 64 banked, on 14 early calls - `rush`'s aggression with `veteran`'s survival, on a layout neither declares.

  The reading is about the board rather than the player: **the S folds, so one block in the middle covers both passes.** That is the board's own thesis, and the layout the harness declares for it spreads anyway. Which is what this milestone said out loud - the harness and the players are not disagreeing, they are measuring different things - arriving one step earlier than the step built to find it. What is *not* claimed: none of it has been replayed, so the wave-by-wave half waits for step 3, and no `player` loadout was declared in the harness, because that would be these tiles without this run.

  Free from step 1: **the determinism gate now compares the log too**, since it compares the whole state and the log lives there.
- [x] Replay - feed a log back through `stepGame` and land on the same verdict, the same core HP and the same Cycles. This is the step that pays for the first two: a replay that does not reproduce is a determinism bug with a reproduction attached, which is the most useful failure this project could have. The gate is a recorded run replaying to an identical `RunReport`.

  **Done, and the answer is the one worth having: the run the player played replays to the same run, zero differences.** `won 5 64 15` in 2:08, reproduced from twenty-nine lines of text. That is the whole milestone's claim landing on a real game rather than on two code paths - `game-loop.test.ts` could only assert that the game's loop and the harness's loop agree; this asserts that a person's run and the instrument's reading are the same run.

  **It goes through the harness rather than beside it.** `runBalance` gave up its loop to `runSimulation(driver, options)`, and a `RunDriver` answers the one question that actually differs: what does the player do this tick. A declared layout spends down a build order; a recorded run replays what somebody did. Writing the loop twice would have been two instruments that have to agree about a reading, which is the shape this project keeps deleting - and it means a replayed run and a declared layout come out as the same `RunReport`, side by side, which is what step 6 needs and now costs nothing. Behaviour-neutral: the whole `npm run balance` table came out byte-identical, checked with `diff` against the previous commit rather than by eye.

  **The comparison is deliberately more than the verdict**, and one tamper is the argument for it. Drop the last upgrade of the flawless run and **the verdict does not move** - still a clear with the core untouched - but the Cycles do (64 left over instead of 94 unspent) and so does the clock (7690 ticks instead of 7721). A gate that compared the ending alone would call that the same run. So the check is the actions the replay managed to take, the enemies that walked through, and then the ending. The input half is free: the replay records its own actions through the same lines in `game.ts` that recorded the original, so an action it could not afford is *missing* rather than merely ineffective.

  **What is not gated, and why.** A placement moved one second later inside the opening lull is genuinely the same run - zero differences - because nothing is in range yet. That is an accident of where the waves happen to be rather than a property worth locking in, so it is written down here instead of asserted. The tamper that is gated moves a tower one tile, which is the board's own thesis as a test.

  A scripted run covers **sell and Overclock**, because two human runs have now touched neither, and a replay that silently skipped both would still reproduce those logs perfectly. And the envelope's two refusals live here rather than in the parser: another curve, and a board this build does not have - "not a log" and "a log of another game" are different answers.
- [x] Overclock in the sim - the caveat printed under every margin table since v1.6, in the harness's own words: *every row is a floor, not a measurement*. `triggerOverclock` is called from `main.ts` and nowhere else, so no reading this project has ever taken has used the ability a player leans on exactly when a wave is going wrong. With replay in hand this stops being guesswork - the question is not "how much is Overclock worth" in the abstract but "how much was it worth in the run that was actually played".

  **Done, and it did not confirm the caveat - it refuted it.** `withOverclock` is a decorator over a `RunDriver`, so the policy lays over a declared layout and over a recorded human run alike, and `--overclock` pairs every row with the same run firing Overclock the moment it is off cooldown.
