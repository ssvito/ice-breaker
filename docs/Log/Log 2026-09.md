Fica `MUSIC .... ANCESTOR SOUNDWORKS` abrindo o site, e o README carrega os dois nomes, porque lá cabe dizer quem fez o quê.

- 2026-09-11: **v1.7 passo 1 - a run virou estado, e o estado é o `null`.** `let state: GameState | null`, e **de propósito não existe um `mode` do lado**. Um booleano que precisa concordar com uma run anulável é duas fontes de verdade para um fato só, e o jeito como isso derrapa é um dos dois ser setado num lugar em que o outro não é - que é exatamente a família de bug sobre a qual este projeto já tem nota. O `resetGame()` virou `startRun()`: mesmo código, nome que parou de supor que sempre existe uma run rodando, e é nele que o descritor de run cai no passo 2.
- 2026-09-11: **a anulabilidade custou umas 25 chamadas e comprou um bug de verdade.** O `spawnArmed` nunca esteve no reset: arma o port, perde antes de tocar nele, toca para reiniciar - e o toque que reinicia sai da função antes da linha que desarma. O board novo abre com as setas acesas. **E não é cosmético**, que foi a minha primeira leitura e estava errada: o tick que limpa arme velho só roda quando não há wave para chamar, e run nova abre *dentro* de uma contagem, então a flag atravessa. O primeiro toque do jogador no port chamaria a wave 1 adiantada sem nenhum dos dois toques de confirmação que o port existe para exigir. Achado escrevendo a lista do que uma run possui, que é o argumento do passo inteiro.
- 2026-09-11: o que fica escondido na shell é o que fala do board - HUD, console, menu de build - e **a coluna da engrenagem fica**, porque som, fullscreen e a build do ABOUT continuam verdade sem run nenhuma. O `clearDisplay()` saiu do `present()` para o `canvas.ts` exportado: frame sem mundo para blitar é só o preto, em vez do último frame de uma run que acabou - que seria a mentira mais convincente que este jogo sabe contar.
- 2026-09-11: **`?shell` entrou como andaime com prazo de validade.** Um estado que nada ainda sabe mostrar é um estado que ninguém consegue olhar, e "não muda nada" verificado só por `tsc` é a versão fraca do checkpoint. Query string e não global de DEV pelo motivo de sempre neste projeto: a verificação acontece no celular, e no celular dá para digitar uma URL e não dá para chamar `window.startRun()`. O `?gallery` é o precedente. O passo 2 põe botão de start na shell e aposenta o parâmetro.
- 2026-09-11: duas coisas que o passo **não** resolveu e que são do passo 2, escritas antes de alguém tropeçar. O loop continua rodando na shell e nada é passado por ele - de propósito, porque parar e religar o rAF é mais caro que um `return` e a shell vai querer animar alguma coisa. E **o teclado continua respondendo sem run**: espaço pausa, `1-4` escolhe torre, `F` troca velocidade. Hoje nada disso é visível (não se desenha nada e o menu está escondido) e o `startRun()` limpa a pausa, então é inerte - mas inerte é diferente de decidido, e quem decide é a tela que vai existir.
- 2026-09-11: `tsc` limpo, 44 testes passando, build ok - e nenhum dos três diz o que o checkpoint pede, porque o checkpoint é "nada mudou jogando". Isso é olho no celular, como sempre.
- 2026-09-11: **v1.7 passo 2 - a shell existe e o boot para nela.** `src/shell.ts`, DOM como todo chrome deste projeto, na mesma voz do console: prompt `>`, nome, cursor piscando. É **estado e não splash** - nada ali tem tempo e nada se dispensa sozinho; o app fica na shell até uma run começar.
- 2026-09-11: **o descritor de run ganhou módulo próprio (`runs.ts`) porque run não é mapa.** Endless é outro *tipo* de run no mesmo mapa e dificuldade é um botão antes da run - os dois pousam ao lado do mapa naquele arquivo, e nenhum dos dois caberia como campo do `LevelData`. O `id` já existe sem ser mostrado: recorde é afirmação sobre uma run, então tem que ter por onde nomear qual.
- 2026-09-11: **lista de um vira botão e não menu**, e o desenho inteiro do picker coube numa expressão: `runs.length === 1 ? 'START' : run.name`, em cima de um loop que já constrói lista. O nome da entrada só é impresso no dia em que existe algo entre o que escolher, que é exatamente o que o roadmap argumentou como não-objetivo. A segunda entrada é uma linha no `runs.ts`.

- 2026-09-11: o `startRun()` passou a receber o descritor, e o board e o `spawnTile` são re-derivados **só quando o mapa sob a run muda**. É condição e não suposição: hoje nunca dispara, porque `RUNS` tem uma entrada, e é por isso que a segunda entrada não pede mudança aqui. O que fica devendo e está escrito: **o viewport continua dimensionado pelo mapa do boot** - um segundo mapa de outro tamanho é a única coisa que vai precisar reconstruir ele, e isso é do v1.8.
