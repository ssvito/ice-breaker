- 2026-08-23: **v1.2 chosen - tower panel + upgrades.** Read `tower.ts` and `main.ts` before picking, same rule as v1.1: a placed tower today has no stats readout, no upgrade, no undo, and its only interaction is `overclockArmed` ("press Q, then click a tower"), which is a keyboard mode in a game that ships a touch toolbar. One selection model is the fix for all four, and [Idea Bank](../Idea%20Bank/Idea%20Bank.md) had already named the tap-tower panel the foundation under upgrades, sell, and touch Overclock. Specced in [Tower Panel](../Design/Tower%20Panel.md), six-step build order in [Roadmap](../Roadmap.md) (selection → panel shell → sell → tiers → Overclock migration → verify). Decisions worth keeping: panel is DOM like the v1 toolbar (native touch handling, the canvas hit-testing alternative bought nothing then either); selection and placement can share one `pointerdown` because `isPlaceable` already rejects `occupied` tiles, so the targets are disjoint; sell tracks `invested` on the entity instead of recomputing from the cost table, which would break the first time costs are rebalanced; tiers extend the per-kind stats table rather than adding a parallel system. Sell lands before upgrades on purpose - it is the smallest mutation that exercises the whole select-act-deselect loop.

- 2026-08-23: v1.2 step 1 done - **selection model.** `selectedTower` in `main.ts`, a new `pointerdown` branch that selects a tower on its tile and clears the selection on any other tap, Escape as the keyboard out, and `drawSelection` in `render.ts` (corner brackets on the tile plus the range circle in the tower's ring color). Brackets rather than a full tile outline so the 28px tower sprite is not boxed in by a border one pixel off its own silhouette. The selection branch sits *after* the `overclockArmed` branch for now so the old arm-then-click flow keeps working until step 5 deletes it. `tsc` clean; **not verified in browser this session** - the Chrome extension was not connected, so the visual check is owed.
- 2026-08-23: v1.2 step 2 done - **panel shell.** New `src/panel.ts` (`createTowerPanel`) rather than more code in `main.ts`, which was already the biggest file; the panel owns its DOM and exposes one `update(tower | null)`. Anchored top-right: the toolbar holds the bottom edge and the HUD text holds the top-left, so that corner was the only one free on a phone in landscape. Rows are built once and rewritten in place instead of re-rendering `innerHTML` each frame - a rebuilt subtree would destroy the buttons steps 3-5 put here, and any tap in flight on them. Aura towers show SLOW as the cut they apply (50%, not 0.5) with no damage/rate rows, since those numbers are meaningless for them. `tsc` clean; browser check still owed.
- 2026-08-23: v1.2 step 3 done - **sell.** `invested` on the `Tower` entity (set to the placement cost, and step 4 will add upgrade spend to it), `SELL_REFUND = 0.6`, `sellValue()` in `tower.ts`. Selling splices the tower, frees its tile in `occupied`, pays the refund, and clears the selection. The panel acts on the tower it is currently showing (a `current` captured by `update`) rather than reading a shared selection variable, so a button pressed after the selection moved cannot operate on a stale tower. Panel buttons reuse the toolbar's button rule in `style.css` instead of a second copy of the 44px-target styling. `tsc` clean; browser check still owed.
- 2026-08-23: v1.2 step 4 done - **upgrade tiers.** `TOWER_STATS` became `TOWER_DEFS` (name + placement + a 3-entry tier ladder per kind), flattened once at module load into the shape `towerStats(kind, tier = 1)` returns - the default keeps every existing call site correct, since all of them ask about placement, and flattening at load keeps the function allocation-free in a function that runs several times a frame. `applyUpgrade` writes the next tier's stats onto the entity and adds its cost to `invested`, so the sell refund follows upgrades for free. Attack towers buy damage + fire rate, auras buy slow + radius; Honeypot's radius climbs 0.6 to 0.8 only, because a wide Honeypot stops being a chokepoint and starts being a second IDS Scanner. Panel shows `TIER n/3` and the next tier's value in its own green column next to the current one. Tier tell on the board is procedural pips along the tile's bottom edge, per spec - no tier sprites this milestone. `tsc` clean; browser check still owed.
- 2026-08-23: v1.2 step 5 done - **Overclock is no longer a mode.** `overclockArmed` and the toolbar's OC button are gone; the panel carries an `OC` button that fires on the tower being shown, absent (not disabled) on aura towers, which have no Overclock to trigger. `Q` survives as a desktop shortcut but now acts on the selection, so the invisible "armed, waiting for a target" state that nothing on screen announced is gone with it. This is the actual mobile fix the milestone was chosen for: two taps with hidden state in between became one tap on a thing that is visibly selected. `tsc` clean; browser check still owed.

- 2026-08-23: **build preview added to the panel** (user's call, mid-milestone, not one of the original six steps). Seeing the panel work made the omission obvious: the game was withholding what a tower does until after you had paid 20 to 45 Cycles to find out. The panel now runs two modes - selected tower, or the kind armed in the toolbar (cost, stats, placement rule) - and stays on screen for the whole game rather than only while something is selected. Build mode is also the only place the placement rule shows, which matters most for Honeypot: on-path only was previously discoverable only by trying it and getting an unexplained red tile. Two knock-on changes: rows went from 3 to 4 so the placement line fits under an attack tower's damage/range/rate, and **toolbar buttons stopped being `disabled` when Cycles are short** - a disabled button swallows its click, so the one tower you cannot afford would be the one tower whose stats you cannot read, which is backwards. They grey out via a class now; `isPlaceable` was already blocking the placement itself, so nothing became placeable that wasn't. `tsc` + `vite build` clean; still unplayed.
- 2026-08-23: **panel restyled as a console and moved into a dock with the toolbar** (user's call). Green-on-black terminal: dot leaders between label and value, scanline overlay, blinking cursor after the tower name, `[-]`/`[+]` collapse. Justified by [Theme](../Design/Theme.md) rather than picked for looks - green is already the powered/active trace color, so the readout glows like a live trace next to the cyan board it describes; no new colors entered the palette (green for live values, amber for the next tier, magenta for "cannot afford", all already in use). System monospace stays: a real terminal face would be a downloaded font, and in an offline-first PWA that would be the only asset in the project able to fail to load.
- 2026-08-23: **reversed the panel's anchoring decision from earlier today.** The spec put it top-right, opposite the toolbar, so the two would never fight for an edge. Watching the layout described back made it obviously wrong: they are one control surface, and opposite corners made the eye cross the whole board to get from "which tower" to "what it does". They now share a bottom-centered `.dock` with one width and one safe-area rule; the dock is `pointer-events: none` so the gap between panel and toolbar doesn't swallow taps meant for the board. The cost is honest and is why collapse exists: the dock is taller than the toolbar was and covers more of the bottom-center of the board. Two layout bugs caught while writing it - `width: max-content` on the dock let the stats grid demand all four columns on one line and stretched the console, fixed with a definite `min(94vw, 320px)`; and `display: flex` on the author side outranks the UA's `[hidden]` rule, so the actions row needed its own `[hidden]` declaration to actually hide in build mode.
